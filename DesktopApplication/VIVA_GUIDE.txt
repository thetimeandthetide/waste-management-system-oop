WASTE MANAGEMENT SYSTEM - VIVA QUICK GUIDE
==========================================

The current implementation is a Java Swing desktop application. Main initializes
MySQL in a SwingWorker, LoginFrame authenticates a user, and WasteManagementGUI shows role-filtered
record and report workspaces. JDBC and MySQL Connector/J connect the Java managers
to MySQL. For the full source-by-source walkthrough, read
CODE_STUDY_PACK.md and ROLE_REPORTS_VIVA_ADDENDUM.md.

IMPORTANT CURRENT BEHAVIOR
- Initial accounts: 13 seeded members and one admin; new members can also self-register.
- New members use Join Clean CET to enter their name, DOB, CET register number, and department. The lowercase first name becomes the username, and an unused area is assigned randomly.
- The generated username_clean password is shown after registration and stored only as a salted PBKDF2 hash. It is predictable and suitable only for this classroom project.
- The admin-only Member directory shows member profile fields and assigned areas. The admin can add more registration areas as CET locations are identified.
- Members can add records, update their own pending records, request completion
  approval, and mark their own pending records invalid. They cannot complete or
  delete records.
- Admin can view all records, add records for members, update pending records,
  approve or reject completion requests, mark records collected directly,
  invalidate records, and delete records after confirmation.
- Each record includes type, description, kg, actual location, and collection time.
- Reports are calculated from COMPLETED records. A member's request stays
  pending until admin approval; pending/invalid rows are excluded.
- Member reports show only their own contribution. Admin reports show total,
  member/category breakdown, area/category breakdown, date filtering, chart, and
  CSV export.
- A member's collection outside their assigned area is shown as their bonus
  contribution. Area totals follow the actual collection location.
- Area reports sum approved kilograms and count records by actual collection
  location. They are not a population estimate or scientific pollution index.
- Reports are computed from the waste table; there is no separate report table
  per person, so totals stay in sync with the source records.
- Admin can broadcast announcements; members have an inbox and per-notice read
  receipts. Completion requests use a separate approval queue whose count
  refreshes every 15 seconds against the shared database.

OOP EXPLANATION
1. Classes/objects: Waste subclasses model collection records; AppUser models the
   signed-in identity; managers and GUI are separate objects.
2. Encapsulation: model fields are private and accessed with getters/setters.
3. Abstraction: Waste is abstract and declares getWasteCategory().
4. Inheritance: OrganicWaste, RecyclableWaste, HazardousWaste extend Waste.
5. Polymorphism: each subclass returns its own category through the same method.
6. Exception handling: database and parsing errors are caught and reported.
7. Packages: model, dao, gui, and main divide responsibilities.
8. Swing events: button ActionListeners call handlers and refresh visible data.
9. `CleanButtonUI` paints button fills and hover/pressed states so action labels remain readable across operating-system styles.

2. Explain the flow: Main/SwingWorker -> DatabaseManager -> LoginFrame -> role-aware GUI ->
   manager/DAO -> JDBC -> MySQL.
3. Show a member view and explain limited access.
4. Add a dated record, update it, and request collection approval; show that it
   remains pending and the admin queue displays it.
5. Sign in as admin, approve it and show the status change; explain only
   completed entries count in reports. Show the direct admin collection action.
6. Show how actual area and assigned territory determine assigned vs bonus
   contribution, then show overall, individual, and
   area reports plus a CSV using the applied date range.
7. Show the announcement inbox and a member read receipt.
8. Show SQL data if time permits; close with limitations and next steps.

DEMO SAFETY
- Use throwaway test rows; deleting a record is permanent.
- Do not show passwords on the recording.
- DOB and student register numbers are personal data. Use test profiles or obtain consent before recording; register numbers are format-checked, not verified against a CET registry.
- The default DB is localhost on each machine. Team-wide data sharing requires
  every installation to point at one secured shared MySQL server.
- Weight/category reports are not a measured pollution index.
- The desktop client has application-layer role checks; a production deployment
  needs centralized authorization and protected server credentials.
